# بطاقات استكمال HRManagement

هذه الحزمة هي مصدر الحقيقة التنفيذي لتحويل المشروع من نموذج مؤسسي متقدم إلى **منتج إنتاج وطني سوري قابل للاعتماد والمنافسة**. تحتوي على 190 بطاقة: 58 بطاقة لتقوية النواة والوصول إلى Pilot، و105 بطاقات للمنتج الوطني العام، و17 بطاقة سورية ملزمة للتشريع والرواتب والعملة والتكامل والسيادة والإطلاق، و10 بطاقات مكمّلة للقيود الخارجية التي لا يملكها فريق التطوير (التوريد والطاقة والاحتيال والسيولة والزمن). لا تُعدّ الوثائق أو وجود الشاشة أو نجاح البناء دليلاً على الاكتمال؛ الإغلاق مرتبط بأدلة قبول واختبارات وتشغيل واعتماد مستقل.

## طريقة الاستخدام

1. تُنشأ كل بطاقة في أداة إدارة العمل بنفس المعرّف والعنوان الواردين هنا.
2. لا تبدأ بطاقة قبل إغلاق اعتمادياتها أو توثيق استثناء معتمد.
3. لا تنتقل المنظومة إلى المرحلة التالية قبل اجتياز بوابة المرحلة كاملة.
4. يرفق المنفذ بالبطاقة روابط Pull Request، ونتائج الاختبارات، وأثر الترحيل أو التراجع، وصور أو سجلات التحقق عند الحاجة.
5. أي تغيير يمس بيانات شخصية أو صلاحيات أو رواتب أو سجلات قانونية يحتاج مراجعة ثانية مستقلة.

## الحقول الموحدة

| الحقل | المعنى |
|---|---|
| المعرّف | ثابت ولا يعاد استخدامه، مثل `SEC-001` |
| الأولوية | `P0` مانع إطلاق، `P1` لازم قبل pilot، `P2` لازم قبل التوسع، `P3` تحسين ونضج |
| الحجم | `S` حتى 3 أيام، `M` حتى أسبوعين، `L` حتى 4 أسابيع، `XL` يجب تقسيمها قبل التنفيذ |
| المسؤول | الدور صاحب التنفيذ، وليس اسم شخص |
| الاعتماديات | بطاقات يجب إغلاقها أولاً |
| النطاق | ما يجب تغييره فعلياً |
| معايير القبول | شروط قابلة للإثبات بنعم/لا |
| التحقق | الاختبارات أو الأدلة التي تمنع الإغلاق الشكلي |

## حالات البطاقة

`Draft → Ready → In Progress → In Review → Security/QA Review → Done`، ويمكن استخدام `Blocked` مع سبب وتاريخ مراجعة واضحين.

## تعريف الجاهزية Ready

- الهدف والنطاق وحدود عدم النطاق واضحة.
- الاعتماديات والمالك والمراجع معروفون.
- قرار البيانات أو API أو UX موثق إن كان التغيير غير تافه.
- توجد خطة ترحيل وتراجع للتغييرات التي تمس قاعدة البيانات أو العقود.
- البطاقة صغيرة بما يكفي؛ أي بطاقة `XL` تُقسم قبل بدء البرمجة.

## تعريف الإنجاز Done

> **قاعدة الإغلاق الملزِمة:** لا تُغلق أي بطاقة عند كتابة سياسة أو قالب أو اختبار نصي.
> تُغلق فقط بعد اجتماع الثلاثة معاً: **(1)** تنفيذ حي في بيئة مطابقة للإنتاج،
> **(2)** ناتج محفوظ قابل لإعادة الإنتاج ومربوط بمعرّف تشغيل CI،
> **(3)** توقيع صاحب صلاحية مسمّى بتاريخ.
> أي بطاقة لا تستوفي الثلاثة تُعاد فوراً إلى `Blocked`.

- استوفيت جميع معايير القبول ولم تُخفَ حالات الفشل خلف warning أو skip.
- توجد اختبارات مناسبة: وحدة، تكامل حقيقي، صلاحيات، ترحيل، أداء أو E2E بحسب الخطر.
- لا توجد أسرار أو بيانات شخصية في السجلات أو fixtures أو artifacts.
- وثقت المراقبة والتنبيه وrunbook والتراجع عندما يغيّر العمل سلوك الإنتاج.
- نجحت بوابات CI كافة، وأُغلقت نتائج SAST/SCA/secret/container scan ذات الصلة.
- وافق مراجع مستقل على بطاقات الأمن والرواتب والخصوصية والتدقيق.

### ما لا يُقبل دليلاً

هذه الأنماط **لا** تُغلق بطاقة ضابط، مهما كان عددها أو لون نتيجتها:

- اختبار يؤكد وجود ملف markdown أو أن نصاً يحوي عبارة.
- اختبار يقرأ ملف JSON سياسة ويؤكد قيمة داخله، ما لم يكن كود الإنتاج يقرأ الملف نفسه في وقت التشغيل.
- استدعاء سكربت `*-validate.ps1` والتأكد من رمز الخروج صفر.
- إنشاء قالب أو harness أو مخطط حزمة أدلة مستقبلية.

السبب المباشر: توكيد أن الوثيقة تشترط ضابطاً ليس إثباتاً أن النظام يطبّقه. مثال موثّق:
اختبار شهادة الرواتب الوطنية كان يؤكد `bankReconciliationRequired: true` في ملف JSON بينما
لا يوجد في النظام كود مطابقة مصرفية إطلاقاً — والاختبار أخضر.

راجع [بروتوكول التدقيق](../AUDIT_PROTOCOL.md) لتفصيل ما يُحتسب دليلاً وكيف يُعرض.

## قاعدة الأولويات

- لا بيانات حقيقية ولا Pilot قبل إغلاق جميع `P0`.
- لا Pilot لجهة واحدة قبل إغلاق `P1` وإثبات العزل والاستعادة وسلامة الرواتب.
- لا توسع لعدة جهات قبل إغلاق `P2` واختبارات الحمل والفشل والتعافي.
- `P3` لا يعني اختياري دائماً؛ بعض بطاقاته تصبح شرطاً قبل الإطلاق الوطني وفق الجهة المنظمة.
- بطاقات `National Gate` و`P0/P1/P2-National` إلزامية للإنتاج الوطني؛ يمكن فقط اعتماد `Not Applicable` بتعليل قانوني/معماري موقع ودليل أن الضابط خارج النطاق.
- لا يعني إغلاق 190 بطاقة أن الجاهزية مضمونة؛ قرار الإنتاج السوري ينتج عن قياسات `NAT-001..008` و`SYR-001..017` على release digest وبيئة ونطاق جهات محددين.

## ما لا تفعله هذه الحزمة

- لا تفترض أن كل ما في وثائق الأطروحة منفذ أو صحيح.
- لا تجعل عدد الخدمات أو عدد الاختبارات مؤشراً وحيداً للنضج.
- لا تستبدل التحليل القانوني الرسمي لقواعد الخدمة والرواتب والاحتفاظ.
- لا تسمح بإغلاق بطاقة عبر اختبار mock فقط عندما يكون الخطر في PostgreSQL أو RabbitMQ أو Keycloak أو MinIO الحقيقي.
