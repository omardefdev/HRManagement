# Event Publisher Inventory (INT-001, PLAN-40)

Every domain event, command and acknowledgement published by the services, and how it stays atomic with the state it
describes. **A plan that adds an event or a publisher adds its row here in the same commit** (rule R4 of
`OutboxPublishOrderingArchitectureTests`) and publishes with one of the patterns below.

## Patterns

| Pattern | Meaning |
|---------|---------|
| **SingleSave** | Change the state, publish, then one `SaveChanges`. The bus outbox writes the `OutboxMessage` row in that save, so state and message commit together. The default (D-40-2): entity ids are generated by the client. |
| **OutboxUnitOfWork** | `OutboxUnitOfWork.ExecuteAsync` (or `IContractsRepository.ExecuteAtomicAsync`): one explicit transaction, for sites that need `ExecuteUpdate`, an intermediate save, or helpers that save inside. It joins an ambient transaction. |
| **ConsumerOutbox** | Published from a consumer or saga (`ConsumeContext`, or `IPublishEndpoint` inside a consume scope). The consumer outbox stores the message in the transaction that commits the consumer's work and sends it after the commit. |

A method that publishes and deliberately does not save carries `[StagesOutboxMessages]`: its caller must save after it (or be
marked itself). Repaired and replayed events use `DeterministicMessageId` (D-40-3).

```csharp
// SingleSave
item.Status = Executed;
await publish.Publish<IThingHappened>(new { ... });
await db.SaveChangesAsync();

// OutboxUnitOfWork: a database-side step or helpers that save
await OutboxUnitOfWork.ExecuteAsync(db, async ct =>
{
    await db.Things.Where(...).ExecuteUpdateAsync(..., ct);
    await publish.Publish<IThingHappened>(new { ... }, ct);
}, ct);
```

Never publish after the last save of a scope, and never save the state, publish, then save again outside one transaction:
a crash between the saves leaves the state committed and the event gone, and a retry is refused because the state changed.

### Party acknowledgements (shared base classes)

`SeparationPartyAckConsumerBase`, `HirePartyAckConsumerBase`, `TransferPartyAckConsumerBase` and
`SecondmentPartyAckConsumerBase` publish `I{Separation,Hire,Transfer,Secondment}Party{Completed,Faulted}` (ConsumerOutbox) for
Records.Archive, IT.Infra, IDCard, HR.Health, Auth.Directory, Admin.Logistics and HR.Movements. A business failure publishes
`*PartyFaulted` once and commits; a transient failure rethrows without publishing while retries remain, and on the last attempt
publishes `*PartyFaulted` once and returns (D-40-6).

### Not called in production

`IEventPublisher.PublishTransactionArchivedAsync`, `PublishSeparationCompletedAsync`, `PublishHireCaseCompletedAsync` and
`ErrorQueueReplay.ReplayAsync` have no production caller: `ITransactionArchived` comes from Records.Archive, and
`ISeparationCompleted` and `IHireCaseCompleted` from the sagas. A future caller of `ErrorQueueReplay` inside an outbox scope
needs a save after it.

## Rules for new publishers (PLAN-40 contract)

- Any plan that adds an event or a publisher adds its row here in the same commit (rule R4) and publishes with one of the
  patterns above. `tests/architecture/outbox-publish-allowlist.txt` stays empty unless a line carries a written reason.
- Publish through the contract interface (`Publish<IThing>(new { ... })`). The outbox delivers to the exchange of the
  published type only: a concrete class goes to its own exchange, which nothing binds to the interface's exchange, and the
  broker drops the message.
- A publish that a later replay must be able to repeat also writes its `PublishedEventLedger` row in the same save and uses
  `DeterministicMessageId`.
