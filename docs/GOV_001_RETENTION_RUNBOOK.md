# Runbook احتفاظ GOV-001

## قبل أي purge

1. تأكيد لا يوجد legal hold نشط (Employee / File / Audit).
2. تشغيل dry-run: `python scripts/gov001-retention-dry-run.py`.
3. مراجعة تقرير JSON تحت `artifacts/gov001-retention-dry-run.json`.
4. تفعيل `AllowPurge` فقط لفترة الصيانة المخططة (تدقيق البوابة).

## ترتيب مقترح

1. Inbox receipts (منخفض الحساسية).
2. File PendingPurge بعد RetainUntil.
3. Gateway audit (بعد WORM export).
4. Anonymize موظفين منفصلين بلا hold (DATA-002).

## أدلة تدقيق متوقعة

- أحداث `AuditPurge` في SecurityAudit.
- سجلات HostedService.
- تقرير dry-run مؤرخ.

## طلبات التوظيف (HCM-030 / PLAN-30 G)

- **القاعدة (زوج الطلب):** طلب التوظيف `RecruitmentApplication` مع طلب البوابة أو الترشّح الداخلي المرتبط به يُعالجان معاً.
  يستحق الإخفاء عندما: لم يُعيَّن المرشح (`HiredEmployeeId` فارغ)، ولا حجز قانوني على أي من الصفين، ولا استئناف معلّق،
  وما زال يحمل بيانات (غير مُخفى، أو مُخفى جزئياً كإخفاء DSAR لصف البوابة وحده، أو بقيت مستندات/رسائل)، ومرّ
  `Recruitment:Retention:Months` (افتراضي 36) على تاريخ البدء: إغلاق الشاغر ?? إلغاؤه ?? تاريخ التقديم. الشاغر المفتوح لا
  يبدأ العدّ. طلبات البوابة القديمة غير المرتبطة تبقى على قاعدة HCM-006 (إغلاق الشاغر ?? تاريخ التقديم).
- **ما يُخفى (معاملة واحدة لكل زوج):** الاسم والرقم الوطني (عناصر نائبة `ANON`) والهاتف والبريد وقناة الإشعار وتاريخ الموافقة
  والنبذة والملف الشخصي (تاريخ الميلاد، المؤهل، التخصص، سنة التخرج، سنوات الخبرة) وملاحظات الطلب والرفض وسبب تجاوز
  الأهلية ومسوّغات الترشّح الداخلي؛ تُحرَّر ملفات `CandidateDocument` عبر outbox مراجع الملفات (TenantId صريح) وتُحذف
  صفوفها؛ تُفرَّغ نصوص `CandidateNotification` ويُوقَف المعلّق منها. يبقى الرقم المرجعي وتواريخ الحالة.
- **المهمة:** `CandidateRetentionJob` أسبوعياً (`Recruitment:Jobs:CandidateRetentionEnabled`،
  `CandidateRetentionIntervalMinutes` = 10080، قفل 8675316، دفعات 100). تفحص المهمة كل ساعة وتعالج كل جهة ليس لها تشغيل
  مهمة **مكتمل** (`FinishedAt` غير فارغ) خلال الفترة، فلا يتكرر التشغيل بعد إعادة التشغيل، والتشغيل المقطوع (إيقاف، إلغاء،
  خطأ عام) يُستأنف للجهات غير المكتملة في الفحص التالي. يُقفل صفّا الزوج (`FOR UPDATE`) قبل إعادة التحقق داخل المعاملة،
  فالحجز القانوني أو الاستئناف أو التعيين المتزامن ينتظر أو يُرى. `AnonymizedCount` يُحتسب مع كل التزام، والتشغيل المقطوع
  يُسجَّل بعدده الجزئي و`FinishedAt` فارغ. `Recruitment:Retention:Apply` = false افتراضياً:
  تشغيل تجريبي يسجّل الأعداد فقط. Acceptance: true (`docker-compose.acceptance.yml`). **Production وStaging تبقى false
  صراحةً حتى موافقة مسؤول حماية البيانات (DPO)**؛ التفعيل تغيير إعداد موثّق بقرار.
- **الشاشة:** `CandidateLifecycle/Index` (دور Admin، سياسة `HrCoreDelete`): قائمة المستحق (المرجع، الشاغر، تاريخ البدء،
  السبب)، «تشغيل تجريبي» للجهة الحالية، «تنفيذ الإخفاء» (بتأكيد داخل الصفحة) فقط عند `Apply=true` (لا يتوقف بإغلاق
  المتصفح أو مهلة البوابة؛ يكتمل ويُسجَّل)، وسجل التشغيل
  `CandidateRetentionRuns` (صف لكل جهة لكل تشغيل: DryRun، Due، Anonymized، SkippedLegalHold، SkippedAppeal، TriggeredBy، Error).
- **قيود معروفة:** معترض التدقيق العام يكتب القيم القديمة للأعمدة غير الموسومة `[AuditRedact]` في `EntityAuditLog` عند
  الإخفاء (موروث)؛ تحت RLS الإنتاج (`hr_core_app`) لا ترى المهام عابرة الجهات الصفوف (موروث لكل مهام التوظيف)؛ تحرير
  الملفات يعتمد على موزّع outbox المراجع (خلل التسليم الموروث موثّق في تسليم الجلسة 2).
